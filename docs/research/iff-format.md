B. GENERATIONS OF THE ".iff" CONTAINER (what is known)
B1. Gen-1 "old IFF" (NBA 2K9-2K14 PC; also College Hoops 2K8/NBA 2K8-era consoles, big-endian). Visual Concepts container: fixed 0x20 header, block table, per-file "data headers", block data, then a trailing name table of UTF-16LE strings with type tags (TXTR, SCNE, AUDO, LAYT ...) and memory-pool tags (DRAM/VRAM/SRAM). Evidence: bep713/2k-tools IFFReader.js (https://github.com/bep713/2k-tools, MIT), confirmed by [LOCAL-PARSE] of its test IFFs and of a real NBA 2K14 PC dorna000.iff from archive.org (details in header_layout). NLSC hex tutorial independently describes the trailing names list with "TXTR, DRAM, VRAM, SRAM, SCOS, AUDO, AUSB, SPCX, SCNE, LAYT, curveanim, SingleMoCap, FxTweakablesV2" labels and says names are at the END of the compressed global.iff (https://forums.nba-live.com/viewtopic.php?f=138&t=81858). Compression on PC 2K11-2K14 = whole-file zlib wrapper that community tools strip ("NBA 2K12 IFF File Decompressor ... decompress the 2K12 iff files for editing ... iff/cdf files now supported" https://forums.nba-live.com/downloads.php?view=detail&df_id=2152 ; ModdingWay "NBA 2K12 Decompressor / Unzlib" https://www.moddingway.com/file/15402/nba-2k12-decompressor-unzlib-v-1-0 ; a 2K12-era decompressor error string "This file is not compressed with ZLIB or it is already decompressed" quoted at https://forums.nba-live.com/viewtopic.php?t=116081). Note: gregkwaste's type table lists a 'ZLIB' ASCII magic 0x5A4C4942 (/tmp/iffsrc/NBA2K17_Explorer/nba2k17commonvars.py) and his ZLIB handler skips 0x10 header bytes before zlib.decompress (/tmp/iffsrc/NBA2K17_Explorer/parsing_functions.py lines 240-244) -> i.e. "ZLIB" + 12 bytes header then raw zlib stream (2K15-2K17 archives; UNCONFIRMED that 2K11-14 PC uses the identical 16-byte wrapper). The CH2K8/PS3 variant parsed by 2k-tools uses a custom LZ77 ("h7a") compressor, NOT zlib (src/util/h7aCompressionUtil.js). Large textures in 2K11-14 live in a sibling .cdf (CDF magic 0x305098F0 in 2k15qt.py; dorna###.iff/.cdf pairs per https://forums.nba-live.com/viewtopic.php?f=154&t=94824; [LOCAL-PARSE] dorna000.cdf starts 67 20 0E AC ... 'DXT1').
B2. Gen-2 "packed IFF" (NBA 2K15-2K24 PC). Game assets moved into monolithic archives 0A,0B,...3H with a 'manifest' text file (gregkwaste/NBA2K17_Explorer 0a.py, manifest.py: archive 0A @0x10 = arch_num, @0x20 item_num, 32-byte archive descriptors, 24-byte item records (uint64 offset, uint32 id0, uint32 size, uint64 id1)). Inside archives, IFF containers are magic 0x94EF3BFF (read big-endian; = bytes 94 EF 3B FF, i.e. the byte-swapped Gen-1 FF 3B EF 94) with 0x38-byte sub-headers (x38header: id0,id1 uint32; type,size,comp_type,start,stop uint64) and sections typed 1=zlib/lzma data, 2=zip, 3=separator; "Zlib Section" when x38.type==0x10 or (type==8 and comp_type in {5,6}) (/tmp/iffsrc/NBA2K15_Explorer/2k15qt.py lines 355-600). Exported/modder-facing .iff files from 2K16 onward are plain PKZIP archives: 'PK\x03\x04' entries using method 0 (stored), 8 (deflate) or 0xE (LZMA; data prefixed by 4 bytes before the LZMA stream) with ordinary local/central headers (parsing_functions.py zip_types = {0xE:'LZMA',0:'NONE',0x8:'ZLIB'}; ziptest.py). Community confirmation: "Only 2k16 to 24 Iff files Can be opened with 7zip" (https://forums.nba-live.com/viewtopic.php?t=116081); 7-Zip workflow: open .iff, pull .dds + .TXTR, edit, drop back, TXTR text file holds width/height/mips/format e.g. BC1_UNORM/BC7 (https://forums.nba-live.com/viewtopic.php?f=291&t=116669 ; https://www.nba-live.com/forums/viewtopic.php?t=117358). Inner files: .dds textures, .TXTR/.RDAT text descriptors, SCNE (JSON-like scene with "Texture": {...,"Width","Height","Mips","Format"}), appearance.json, gz model files (https://forums.nba-live.com/viewtopic.php?f=258&t=109638 ; https://forums.nba-live.com/viewtopic.php?f=287&t=115652). Loose-file override: 2K15-2K24 need Looyh's NBA2K_Hook dinput8.dll VFS to load Mods/*.iff (https://bbs.eyeuc.com/down/view/20273 ; https://forums.nba-live.com/downloads.php?df_id=11677&view=detail).
B3. Gen-3 (NBA 2K25-2K26). Looyh: "NBA2K25 file structures have changed significantly, so almost all files need to be transcoded, and IFF files are dynamically built into zip-format IFF during export"; textures are .tld (converted to .dds), models .gz (converted to .bin), names carry 64-bit hashes e.g. face_color_o.63b97fbfa62967c6.tld, binary SCNE metadata -> JSON (https://forums.nba-live.com/viewtopic.php?f=291&t=116315). Closed-source 2K25/26 IFF repacker: Mr.Star's "IFF Data Processing Tool" (paid, ko-fi) edits hihead/appearance_info/mathnodes nodes and repacks preserving structure (https://forums.nba-live.com/viewtopic.php?f=297&t=117272 ; https://ko-fi.com/s/2239f8d521).

C. SUB-FILE TYPE TAGS seen: TXTR, SCNE, AUDO, LAYT, MRKS, PRIV, TXT, DRCT, CLTH, AMBO, HILT, NAME, CDAN (2k-tools IFFType.js); plus SCOS, AUSB, SPCX, curveanim, SingleMoCap, FxTweakablesV2 (NLSC t=81858). Memory-pool tags: DRAM, VRAM, SRAM.

## Header layout
GEN-1 "OLD IFF" (NBA 2K9-2K14 PC little-endian; CH2K8/2K8-era consoles big-endian). Source: bep713/2k-tools src/parser/IFFReader.js + IFFWriter.js (MIT) and [LOCAL-PARSE].
Offset 0x00 u32 magic: bytes 30 50 98 F0 on real NBA 2K14 PC dorna000.iff (= 0x305098F0 BE / 0xF0985030 LE; gregkwaste labels this value 'CDF' = IFF whose texture payload lives in sibling .cdf). CH2K8 PS3 sample IFFs: bytes FF 3B EF 94 (0xFF3BEF94 BE). NBA 2K15-17 archive IFFs: 0x94EF3BFF when read BE (gregkwaste type_dict) = same magic byte-swapped. UNCONFIRMED: whether standalone 2K11-14 PC texture IFFs (png####, uh###) use FF3BEF94-swapped or 305098F0 — only dorna (cdf-paired) files were parsed locally.
0x04 u32 headerSize (dorna000.iff: 546 = 0x222; block data starts exactly there)
0x08 u32 fileLength, ALWAYS big-endian per 2k-tools ("File length is always BE"); dorna000.iff: 0x00000222 = 546 (header-only, since data is external in .cdf); two-files.iff: 23555 of 23825 bytes (excludes trailing name table).
0x0C u32 zero
0x10 u32 blockCount (dorna000: 1; s000.iff: 2)
0x14 u32 unk1 (0x0D in CH2K8 samples, 0x15 in 2K14 PC)
0x18 u32 fileCount (dorna000: 14 sub-files; s000.iff: 11)
0x1C u32 unk2 (0x25/0x45 in CH2K8 samples; 0x2D in 2K14 PC)
[2K14 PC ONLY, observed] 0x20 u32 = 0x141, 0x24 u32 = 0x1E5 — two extra dwords not present in the CH2K8 layout (look like intra-header offsets; UNCONFIRMED meaning). Block table then starts at 0x28 in 2K14 PC, at 0x20 in CH2K8.
Block table: blockCount x 0x20 bytes: u32 name/hash (constant 0xBB05A9C1 for block0 and 0x411536D5 for block1 in every sample incl. 2K14 PC), u32 type (same value repeated), u32 unk1 (0x10 in 2K14 PC), u32 uncompressedLength, u32 unk2, u32 startOffset (dorna000: 546 = headerSize), u32 compressedLength (== uncompressed when stored), u32 isIndexed.
Then fileCount x u32 dataFileOffsets (dorna000 @0x48: 57,69,81,93,... step 12), then per-file data headers: u32 id (hash, e.g. 0x309D34BC), u32 typeRaw (e.g. 0x5C369069), u32 offsetCount, then offsetCount x u32 offsets into the block(s). Sub-file lengths are derived by sorting offsets and differencing against next offset / block length (IFFReader._onDataHeaderBlocks).
Block data at startOffset. In CH2K8 a compressed block begins with its own 20-byte BE header (magic, uncompressedLength, compressedLength, unk, shiftAmount) followed by custom LZ77 ("h7a") data — NOT zlib. In NBA 2K11-14 PC the whole .iff is instead zlib-wrapped on disk and community "decompressors" strip it (NLSC df_id=2152; ModdingWay unzlib). For 2K15-17 archive IFFs gregkwaste finds a 16-byte 'ZLIB'+12-byte header then zlib stream (parsing_functions.py ZLIB branch seeks 0x10 then zlib.decompress).
Trailer (after last block): u32 magic + u32 LE size, then name table: u32 numNames, u32 offset-to-names (offsets are relative to their own position minus 1), per entry: u32 ptr -> {u32 ptr to UTF-16LE name, u32 ptr to UTF-16LE 4-char type tag}. Observed tail strings in dorna000.iff: "dorna000.cdf", "slot00".."slot11", each followed by "TXTR","DRAM","DRAM" (textures referencing the external .cdf). NLSC t=81858 confirms names (with 00 interleave = UTF-16) sit at the end of the compressed file and that everything after the "0,1,2" entries is hex-only "hidden" data.
Sibling .cdf (2K11-14): raw texture payload; dorna000.cdf = 2,450,336 bytes beginning 67 20 0E AC 00 00 00 00 'DXT1' ... (DXT1 blocks); UNCONFIRMED exact cdf header fields. 2k15qt.py cdf_file_entry = {u64 off, u64 size, 8 skip, u64 pad} and CDF file name stored as UTF-16 at sub_heads[-1].

GEN-2 ARCHIVE IFF (2K15-2K24 inside 0A..3H): magic 94 EF 3B FF; u32 header_length (LE); u32 next_off (BE); 4 skip; u64 sub_head_count; u64 s (x38 table offset = s + pos - 9; head_count = (s-9)/16); u64 file_count; u64 relative pointer(s) to sub-head data; then sub_head_count x 0x38-byte x38header {u32 id0, u32 id1, u64 type, u64 size, u64 comp_type, u64 start, u64 stop, u64 zero}; file entries {u32 id0, u32 id1, u64 type(1=zlib/lzma data: +u64; 2=zip: +2xu64; 3=separator: +3xu64)} (2k15qt.py lines 355-600). Exported .iff = standard ZIP (PK\x03\x04 / PK\x01\x02 / PK\x05\x06), methods 0/8/0xE(LZMA, 4-byte prefix) (parsing_functions.py).

GEN-3 (2K25/26): not publicly documented in source; only tool descriptions (transcoded .tld/.gz, hashed names, zip-format IFF on export, stricter compression validation after 2K26 1.4). UNCONFIRMED beyond those statements.

## Roster / save format
LEGACY FILE-BASED ROSTERS (NBA 2K10-2K14 PC .ROS and roster.iff):
- Checksum: first 4 bytes of a save/roster = CRC32 of everything after byte 4; file size must not change (JaoSming, "Hex Editing: Dealing with Checksums" https://forums.nba-live.com/viewtopic.php?f=138&t=81502 ; Leftos "Hex Editing Rosters" https://forums.nba-live.com/viewtopic.php?p=1552460 : "Select the whole file except the first 4 bytes ... CRC32 ... type in the checksum as you see it"). [LOCAL-PARSE] NBA 2K14 NCAA22.ROS (2,672,672 bytes): bytes 0-3 = 45 9D 39 65; zlib.crc32(data[4:]) = 0x459D3965 -> CRC32 stored big-endian/byte order as displayed. All 2K14 .ROS files in the UBR pack are exactly 2,672,672 bytes (7z listing of archive.org nba-2k14-mod PART3).
- Player table is bit-packed, not byte-aligned: 2K13 player entry = 477 bytes + 5 bits (Leftos, t=88190). Signature skills = 6-bit enums laid out 6+6+14(zero)+6+6+6 bits. Team ID = roster-order index 17 bits after a 10000101 marker; free agents all zeros. Portrait ID = SS1 offset - 300 bytes - 2 bits (u16); CF ID = PortraitID + 30 bytes (u16); GenericF = CFID + 96 bytes + 1 bit (1-bit bool).
- Ratings: one byte each, stored = (Rating - 25) * 3, i.e. file 0-255 maps to game 25-110 (Leftos t=88190; JaoSming "RosRating/3 + 25" https://forums.nba-live.com/viewtopic.php?f=154&t=92732). In 2K13 roster.iff Shot Inside is +352 bytes from entry start; in .ROS it is +14 bytes 3 bits after first signature skill. HoS profile rating order starts: 0 Close Shot, 1 Medium Shot, 2 Ball Handling, 3 3pt Shot, 4 Free Throw, 5 ??? (t=92732). Overall is not stored ("generated in-game"); RED MC exposes Overall_I "Always equals to 1 in ROS files" (https://www.forums.nba-live.com/viewtopic.php?f=151&t=94706).
- roster.iff (the game-folder default roster, 2K12-2K14) must be zlib-decompressed with NBA2KX Mod Tool before editing with Hex on Steroids; same field layout as .ROS but byte-shifted (t=92732; t=88190 "Same exact format as 2k12 in the iff file").
- Tools: REDitor II (2K10-2K12), RED MC (2K13/2K14, also reads "resource-containing IFF files"), both free since Dec 2018 (https://www.nba-live.com/red-mc-reditorii-updated-free/); Sigil 2K14 (2026, roster + career editor, repacks jersey/logo .iff) https://www.nba-live.com/tag/red-mc/ ; 2KVenueLab legacy editor opens PC .ROS for 2K9-2K14, "Repair supported roster checksums", NBA 2K14 default layout only "Partial", RED-MC-shifted layouts "Research" (https://forums.nba-live.com/viewtopic.php?t=117401). 2K14 cheat-table style: Hexorg 2k15v3_846.ct shows 7-bit BitLength fields (memory).
